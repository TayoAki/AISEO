# Compose RankSEO on Railway, not InsForge

Rebuild RankSEO as a composed stack and do not build it on InsForge. Put Next.js, a pipeline worker and Postgres in one Railway project. Use Better Auth 1.7.7 or later with its Stripe plugin. Keep quotas, entitlements and the report state machine in your own SQL, replace the orchestration vendor with a Postgres-backed job queue, and call Claude directly. Four defects make today's build unsafe to charge for: a racy count-then-create quota, a paywall enforced only in the browser, unverified sign-ups that spend real money, and pipelines that save wrong reports as complete. No platform sells fixes for these. InsForge, Supabase and Convex all leave them to code you write, so the platform decision turns on what remains: the 15-minute Bright Data wait, abuse controls, operability and maturity. InsForge is weakest exactly there. It has no queue or workflow primitive, edge functions meant for short jobs, no documented CAPTCHA or auth rate limits, Payments and long-running Compute still in preview, and seven-day backups with no documented point-in-time recovery. It is also a six-person company founded in 2025 whose new $8M seed was announced for a different product. Supabase is the mature BaaS, but its 400-second function ceiling forces a separate worker for the wait anyway, and Convex has the best built-in durable wait but swaps Postgres for a proprietary document model. The composed stack costs an estimated $20 a month in platform fees at launch. It keeps every component on one private network that the Railway MCP server already connected to Claude Code can operate, and it lets the report row, the quota reservation and the pipeline job commit in one transaction. The cost is a small job engine you own, Railway's rough 2026 reliability record and Better Auth's heavy advisory churn. Each has a specific mitigation.

## Every platform leaves RankSEO's riskiest code to you

RankSEO sells two reports that spend money before anyone sees a result. A keyword report runs one Bright Data Perplexity collection and one Claude call; a visibility report sends five prompts each to ChatGPT and Gemini and makes two Claude calls ([RankSEO repository](https://github.com/TechWithEmmaYT/AI-SEO-Marketing-SaaS-App)). At Bright Data's pay-as-you-go **$1.50 per 1,000 records** ([Bright Data](https://brightdata.com/products/web-scraper/ai)), scraping costs about 0.15 cents per keyword report and 1.5 cents per visibility report. Claude costs more. At an assumed 10–20k input tokens it comes to roughly **$0.05–0.11 per report on Sonnet 4.6**, priced at $3/$15 per million tokens ([Anthropic](https://platform.claude.com/docs/en/about-claude/pricing)). The current build gives that spend away. Sign-up needs no email verification, and the spending routes have no rate limit. Quota is checked by counting rows and then inserting one, so parallel requests all pass, and failed reports still count against quota. Paid sections reach every free user's browser, where a React component merely hides them ([RankSEO repository](https://github.com/TechWithEmmaYT/AI-SEO-Marketing-SaaS-App)). The threat is current: Stripe measured a **40% rise in attempted multi-account abuse at AI subscription companies between January and June 2026** ([Stripe](https://stripe.com/blog/what-stripe-data-shows-about-fraud-at-ai-startups)), with **7.4% of sign-ups at AI companies** implicated in suspected multi-accounting ([Stripe](https://stripe.com/blog/analyzing-first-party-fraud-trends-account-free-trial-and-refund-abuse)).

No billing product closes these holes for you. The Better Auth Stripe plugin stores and returns a plan's `limits` object but never enforces it, as the 1.7.7 source confirms ([npm](https://registry.npmjs.org/@better-auth/stripe/-/stripe-1.7.7.tgz)). Stripe Entitlements are feature flags with no quantity ([Stripe](https://docs.stripe.com/billing/entitlements?dashboard-or-api=api)). Polar grants credits but "doesn't block usage" ([Polar](https://polar.sh/docs/features/usage-based-billing/credits)). InsForge Payments mirrors Stripe into Postgres and leaves entitlements to triggers you write ([InsForge](https://docs.insforge.dev/core-concepts/payments/stripe)). Autumn is the one layer with an atomic reserve-confirm-release lock ([Autumn](https://docs.useautumn.com/documentation/customers/balance-locking)). By default, though, its `check()` returns `allowed: true` on timeouts and 5xx errors ([Autumn](https://docs.useautumn.com/documentation/fail-open)), which is the wrong default when every report costs money. Its price also jumps from $0 to **$375 a month** above $8K of monthly billing volume ([Autumn](https://useautumn.com/pricing)). Whatever the platform, the quota lives in your database.

Postgres makes that quota race-free in a single statement. Under the default READ COMMITTED isolation, a concurrent `UPDATE` waits for the first writer and then **re-checks its `WHERE` clause against the updated row** ([PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html)). As a result, `UPDATE quota_bucket SET reserved = reserved + 1 WHERE … AND used + reserved < quota RETURNING …` cannot oversell. Run it in the same short transaction as the report insert, and deduplicate the insert by idempotency key with `INSERT … ON CONFLICT DO NOTHING RETURNING` ([PostgreSQL](https://www.postgresql.org/docs/current/sql-insert.html)). Commit the reservation when the report succeeds and release it when the pipeline fails, so failed reports never consume quota.

Free users get one bucket per feature that never resets: two keyword searches and two visibility scans. Pro (100 keyword, 25 visibility) and Plus (500 and 100) get monthly windows anchored to the subscription start, not today's UTC calendar month. That anchoring also gives annual subscribers twelve monthly allowances instead of one. The Better Auth subscription row already stores `periodStart`, `periodEnd` and `billingInterval` ([Better Auth](https://raw.githubusercontent.com/better-auth/better-auth/main/packages/stripe/src/schema.ts)). That spares you Stripe's 2025 move of period fields from subscriptions to subscription items ([Stripe](https://docs.stripe.com/changelog/basil/2025-03-31/deprecate-subscription-current-period-start-and-end)).

That is the reason to leave MongoDB. Mongo can guard one counter with `$inc` and a `$lt` filter, which on its own would fix today's race. The rebuild, though, needs the reservation, the report row and the job that runs it to commit together. The current Prisma-on-Mongo setup also has no migrations and only emulated foreign keys, and it stores user IDs as ObjectIds in some collections and strings in others ([RankSEO repository](https://github.com/TechWithEmmaYT/AI-SEO-Marketing-SaaS-App)). Postgres suits the auth layer too, since Better Auth 1.7 moved one-time codes, counters and rate limits onto atomic conditional writes ([Better Auth](https://better-auth.com/docs/guides/1-7-upgrade-guide.md)). The move itself is an ETL job. Keep user IDs as stable strings. The Stripe plugin links customers through the user ID stored in Stripe metadata, and an open issue reports it creating duplicate customers when that link breaks ([GitHub](https://github.com/better-auth/better-auth/issues/10434)). Sessions can simply be dropped.

Entitlements follow the same logic. OWASP's API3:2023 describes the current bug exactly, an endpoint that returns every property of an object, and prescribes returning only the properties each caller may see ([OWASP](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization)). Resolve the tier on each request from the stored subscription row, and build responses from a per-tier allowlist. Have background jobs return only a job ID. Better still, don't generate paid sections for free users at all, which also trims their Claude bill. Platforms whose browser SDK queries tables directly make this harder. Row-level security cannot hide columns, and Supabase itself steers users away from column privileges and toward separate tables ([Supabase](https://supabase.com/docs/guides/database/postgres/column-level-security)). A database only your server can reach leaves exactly one place where paid fields can leak.

## InsForge handles the easy half and skips the hard half

InsForge is an Apache-2.0 backend in Supabase's mould: Postgres 15 behind PostgREST 12.2, Deno edge functions, and ten products driven through a CLI and a remote MCP server built for coding agents ([GitHub](https://github.com/InsForge/InsForge); [InsForge](https://docs.insforge.dev/core-concepts/database/overview)). Several products wrap other vendors. The Model Gateway is "OpenRouter-backed" ([InsForge](https://docs.insforge.dev/products)), Sites deploys to Vercel ([InsForge](https://docs.insforge.dev/core-concepts/sites/overview)) and Compute runs on Fly.io ([InsForge](https://docs.insforge.dev/faq)). A single invoice does not shorten the dependency chain. The agent tooling is genuine: every CLI command speaks `--json`, migrations are SQL files and `insforge.toml` holds configuration as code. Each branch gets its own Postgres, and a Backend Advisor proposes SQL fixes ([InsForge](https://docs.insforge.dev/agent-native/overview)). The exit is genuine too, because every project exposes a direct Postgres connection string that works with `pg_dump` and Prisma ([InsForge](https://docs.insforge.dev/faq)).

The gaps line up with RankSEO's hard requirements. **InsForge has no queue, workflow engine or wait-for-webhook primitive.** Its docs say edge functions "are for request/response and short-lived jobs" and send queue workers to Compute ([InsForge](https://docs.insforge.dev/core-concepts/functions/overview)). The cloud function timeout is undocumented today. A since-removed page said 30 seconds, and the self-hosted default is 60 ([InsForge](https://raw.githubusercontent.com/InsForge/InsForge/main/.env.example)). Schedules run on pg_cron at a one-minute minimum. The two docs disagree on retries: the schedules page says "failed runs are logged but not retried", while the functions overview promises retries ([InsForge](https://docs.insforge.dev/core-concepts/functions/schedules); [InsForge](https://docs.insforge.dev/core-concepts/functions/overview)). Compute, the only home for a long-running worker, is a **private preview** with one instance per service and no persistent volumes ([InsForge](https://docs.insforge.dev/core-concepts/compute/overview); [GitHub](https://github.com/InsForge/InsForge)). The 15-minute wait would therefore become a hand-built state machine on these primitives, or Trigger.dev would stay on as an extra vendor.

Auth, payments, AI and backups have gaps of their own. Abuse protection is thin. Email verification can be required, but InsForge's 1.1 MB full documentation never mentions CAPTCHA or Turnstile. The "brute-force throttling" it advertises comes with no numbers ([InsForge](https://docs.insforge.dev/llms-full.txt); [InsForge](https://docs.insforge.dev/core-concepts/authentication/overview)). Payments launched in **private preview on 6 May 2026** ([InsForge](https://insforge.dev/blog/insforge-payments)). The gateway reaches Claude only through OpenRouter. Its own proxy routes are deprecated and structured output is undocumented ([InsForge](https://docs.insforge.dev/sdks/typescript/ai)). Backups run daily with **seven-day retention**, exclude Storage, take the project offline to restore, and include no documented point-in-time recovery ([InsForge](https://docs.insforge.dev/core-concepts/database/backups)).

The company is the larger risk. Y Combinator lists InsForge in its **Spring 2026 batch, founded in 2025, with six people** ([Y Combinator](https://www.ycombinator.com/companies/insforge-instacloud)). Its CLI is at version 0.2.8 ([npm](https://www.npmjs.com/package/@insforge/cli)), and its homepage names no production customers ([InsForge](https://insforge.dev)). Its own security page tells buyers to confirm the SOC 2 report, the SLA and backup RPO/RTO before production use ([InsForge](https://agents.insforge.dev/security.md)). On 29 September 2026 the CEO announced an **$8M seed for InstaCloud**, a new agent-native serverless cloud ([Runtimewire](https://runtimewire.com/article/instacloud-8m-seed-agent-cloud)). The YC listing now reads "InsForge (InstaCloud)", and the SDK's last npm release was on 31 July ([npm](https://www.npmjs.com/package/@insforge/sdk)). The backend still ships, most recently v2.3.3 on 6 October ([GitHub](https://github.com/InsForge/InsForge/releases)), so a pivot is an inference rather than a fact. Still, a solo developer cannot afford to put a paid product's system of record on a roadmap whose new money points elsewhere.

The agent-native edge is narrower than the marketing suggests, and every benchmark behind it is vendor-run. InsForge ran 21 tasks from the academic MCPMark suite ([arXiv](https://arxiv.org/abs/2509.24002)) with Sonnet 4.6. Its MCP server passed all four runs on **42.86% of tasks against 33.33% for Supabase's**, using **7.3M versus 17.9M tokens** ([InsForge](https://insforge.dev/blog/mcpmark-benchmark-results-v2)). The post does not give the competitor's server version, and nobody has replicated the result. InsForge's own June 2026 benchmark put its MCP server **behind Supabase's, 23 to 24 of 30 tasks**; only its CLI-plus-Skills path came out ahead, at 27 ([InsForge](https://insforge.dev/blog/agent-benchmark-first-look)). Both suites measure database chores, not auth, billing, jobs or uptime.

The security model worries more. The dashboard's "Install in Agent" prompt embeds a `uak_` key that "grants full access to your account" ([InsForge](https://docs.insforge.dev/faq)). Docs pages carry a hidden "IMPORTANT FOR AI AGENTS" instruction to fetch a remote skill file ([InsForge](https://docs.insforge.dev/introduction.md)). The founder described scoped agent keys as still upcoming in mid-2026 ([Hacker News](https://news.ycombinator.com/item?id=48181342)).

InsForge's real strengths deserve weight. Database triggers push realtime events to WebSocket channels guarded by row-level security ([InsForge](https://docs.insforge.dev/core-concepts/realtime/overview)), Stripe state is mirrored into Postgres with a verified webhook ledger, and an official bridge lets Better Auth replace native auth ([InsForge](https://docs.insforge.dev/integrations/better-auth)). Self-hosting under Apache-2.0 is a fallback, and prices are low: Pro costs $25 a month plus an hourly instance from $5, or roughly $35–55 a month for a production project ([InsForge](https://insforge.dev/pricing)). But the lowest-risk RankSEO configuration on InsForge routes around nearly every native feature: Better Auth for CAPTCHA and rate limits, Trigger.dev for the wait, Claude called directly, Next.js hosted elsewhere and nightly independent dumps. That reduces InsForge to a host for Postgres and realtime, a role that Railway Postgres with point-in-time recovery and a small SSE endpoint fill with fewer vendors, from a better-funded operator audited for SOC 2.

## Supabase hits a 400-second wall; Convex trades away portability

Supabase is the mature version of the same idea. It raised **$500M at a $10.5B valuation in June 2026** and cites more than 9M developers ([Orrick](https://www.orrick.com/en/News/2026/06/Supabase-Raises-500-Million-at-10-5-Billion-Valuation-to-Accelerate-Lead-in-Agentic-Infrastructure)). Its auth ships Turnstile and hCaptcha ([Supabase](https://supabase.com/docs/guides/auth/auth-captcha)) and configurable per-IP rate limits ([Supabase](https://supabase.com/docs/guides/auth/rate-limits)). A Before User Created hook can reject sign-ups by domain or IP ([Supabase](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook)). Its one-click Stripe Sync Engine now lives under Stripe's own GitHub organisation ([Supabase](https://supabase.com/blog/stripe-sync-engine-transfer)). Its hosted MCP server offers OAuth, read-only mode, project scoping and branching ([Supabase](https://supabase.com/docs/guides/getting-started/mcp)).

The wall is compute. Edge Functions must respond within 150 seconds and stop at **400 seconds of wall-clock time on paid plans, with 2 seconds of CPU per request** ([Supabase](https://supabase.com/docs/guides/functions/limits)). Asked about five-minute LLM calls, a Supabase maintainer answered "No you can't increase it" ([GitHub](https://github.com/orgs/supabase/discussions/40074)). RankSEO's wait would have to be rebuilt from pgmq queues, pg_cron jobs and state columns, or moved to a worker on another host. Once that worker runs on Railway or Fly, the design has become the composed stack, spread across two platforms instead of one. Smaller frictions add up. The built-in mailer sends only **two emails an hour**, so verification needs custom SMTP from day one ([Supabase](https://supabase.com/docs/guides/auth/rate-limits)). The Pro spend cap excludes compute ([Supabase](https://supabase.com/docs/guides/platform/cost-control)). Supabase plus one Railway worker is the credible runner-up. It suits a team that values managed auth with CAPTCHA and sign-up hooks more than a single platform and a portable auth layer.

Convex fits the hardest requirement best. Its Workflow component persists state after every step and survives server restarts. A workflow pauses on `step.awaitEvent` until another function calls `sendEvent` ([GitHub](https://github.com/get-convex/workflow)), which an HTTP action receiving the Bright Data webhook can do. Reactive queries stream progress with no extra code, and mutations are transactions. The Rate Limiter component "fails closed" ([Convex](https://www.convex.dev/components/rate-limiter)), and a local MCP server keeps production access off by default ([Convex](https://docs.convex.dev/ai/convex-mcp-server)). The company is smaller but well funded, with a $57M Series B in August 2026 and $110.5M raised in total ([Dealroom](https://dealroom.co/news/142974-convex-raises-57m-series-b-for-its-ai-optimised-app-backend/)).

The costs fall on portability and discipline. Data lives in Convex's document model. The self-hosted backend carries the source-available **Functional Source License** ([GitHub](https://github.com/get-convex/convex-backend/blob/main/LICENSE.md)), and Pro costs **$25 per developer per month** ([Convex](https://www.convex.dev/pricing)). Workflows must stay deterministic, so changing a workflow's steps breaks the reports in flight. Each workflow can also pass only 1 MB of step data ([GitHub](https://github.com/get-convex/workflow)). Convex's own migration guide names its components as the hardest part to leave ([Convex](https://stack.convex.dev/how-hard-is-it-to-migrate-away-from-convex)). Convex suits a team that wants built-in workflows and reactivity more than it wants Postgres. RankSEO's money-backed SQL points the other way.

The rest of the field trails. Appwrite moved onto Postgres in its 2.0 release on 31 August 2026, six weeks before this report ([Appwrite](https://appwrite.io/blog/post/announcing-appwrite-2)). Nhost caps Pro functions at 180 seconds ([Nhost](https://nhost.io/pricing)). Firebase allows 60-minute HTTP functions ([Firebase](https://firebase.google.com/docs/functions/quotas)) but is NoSQL-first. In April 2026, an unrestricted Firebase browser key ran up a €54k Gemini bill in 13 hours for one developer ([Hacker News](https://news.ycombinator.com/item?id=47791871)).

## One Railway project runs the whole product for about $20 a month

The recommendation in one view, with each choice explained below:

| Layer | Choice | Settings that matter |
|---|---|---|
| Hosting | Railway Pro project with `web`, `worker` and `postgres` services | Dockerfile builds, drain time set, one web replica at launch, soft spend alert |
| Data | Railway Postgres through Prisma or Drizzle | PITR on, nightly offsite `pg_dump`, typed tables with versioned JSONB results |
| Auth | Better Auth 1.7.7 or later | Required verification, Turnstile, database-backed limits, explicit IP header, disposable-domain block |
| Billing | `@better-auth/stripe` on Stripe direct | `onEvent` for failed invoices, reserve-commit-release quota buckets, per-tier serializer |
| Jobs | pg-boss in `worker` | Transactional enqueue, webhook-driven continuation, timeout job, reconciler |
| Progress | SSE fed by LISTEN/NOTIFY | Heartbeats every 15–30 s, `Last-Event-ID` resume, polling fallback |
| LLM | Anthropic API, model chosen by eval | Native structured outputs, local Zod validation, no sampling overrides on Sonnet 5.5 |
| Agent ops | Railway MCP and CLI, Better Auth docs MCP, Stripe MCP, ECC reviewers | OAuth-scoped tokens, restricted production, human approval for deletes and deploys |

### Three services share one private network

Put the rebuild in a single Railway Pro workspace. It costs **$20 a month including $20 of usage**, with unlimited seats for a small team; memory costs about $10 per GB-month and CPU about $20 per vCPU-month, billed on actual use ([Railway](https://railway.com/pricing)). The workspace holds three services. `web` is a Next.js standalone server on 16.4 or later, because the current pin, 16.2.12, sits inside critical image-optimizer advisories that 16.4.0 fixes ([RankSEO repository](https://github.com/TechWithEmmaYT/AI-SEO-Marketing-SaaS-App)). `worker` runs from the same repository with a different start command and no public domain, and `postgres` is Railway's template with point-in-time recovery switched on. Railway's own full-stack Next.js guide documents this layout ([Railway](https://docs.railway.com/guides/fullstack-nextjs)), and because new Railway databases have shipped without a public TCP proxy since 31 July 2026, everything talks over the private network ([Railway](https://railway.com/changelog/2026-07-31-railway-plugin-for-chatgpt)).

A long-running server removes serverless timeouts, but you inherit three chores. Set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`, because the default drain is **zero seconds** and a redeploy otherwise kills in-flight work ([Railway](https://docs.railway.com/deployments/deployment-teardown#draining-time)). Stay on one web replica until traffic demands more, because several Next.js instances need a shared cache handler, a fixed Server Actions encryption key and a `deploymentId` ([Next.js](https://nextjs.org/docs/app/guides/self-hosting)). And switch on database safety yourself, since Railway's responsibility matrix lists backups, PITR and HA as things the "user turns on" ([Railway](https://docs.railway.com/databases#what-railway-manages)). PITR keeps about four weeks of history and costs nothing beyond its storage and WAL egress ([Railway](https://docs.railway.com/volumes/point-in-time-recovery)). Add a nightly `pg_dump` to a bucket outside Railway, because Railway's own guide warns that "only offsite logical dumps survive deleting the project itself" ([Railway](https://docs.railway.com/guides/postgres-backups-restores)). Redis is unnecessary at launch.

### Better Auth 1.7.7 closes the abuse gaps if requests reach its router

Better Auth is the right identity layer. It is MIT-licensed and draws about **11.8M npm downloads a week** ([npm](https://api.npmjs.org/downloads/point/last-week/better-auth)). It keeps users and sessions in your own Postgres. It is now owned by Vercel, which says the library stays open source and platform-agnostic ([Vercel](https://vercel.com/blog/vercel-acquires-better-auth)). Practitioners who left hosted auth make the same case. Val Town moved from Clerk to Better Auth in 2026 after hitting an account-wide limit of five requests per second and concluding that "if Clerk goes down, the whole website goes down". It has reported no outages or bugs since ([Val Town](https://blog.val.town/better-auth)).

Configure it in five moves. Pin **1.7.7 or later**: it is the only line with fixes for September's advisories, including the Postgres rate-limit race and the Critical GHSA-965c, which applies only when magic link and social login are both enabled and has no listed 1.6 backport ([GitHub](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm)). Turn on `requireEmailVerification`, which answers unverified sign-ins with a 403 ([Better Auth](https://www.better-auth.com/docs/concepts/email)), and create a user's free buckets only after verification. Add the captcha plugin with Cloudflare Turnstile, which is free with unlimited verifications ([Cloudflare](https://developers.cloudflare.com/turnstile/plans/)) and by default guards sign-up, sign-in and password reset ([Better Auth](https://www.better-auth.com/docs/plugins/captcha)); check a Turnstile token on report creation for free users as well. Keep the built-in rate limiter, which runs in production and, in the 1.7.7 code, allows **3 requests per 10 seconds per IP on sign-in and sign-up** and 3 per minute on email-sending routes ([npm](https://registry.npmjs.org/better-auth/-/better-auth-1.7.7.tgz)); move its counters to the database once you run two replicas, a path whose Postgres race was fixed in 1.7.7 ([GitHub](https://github.com/better-auth/better-auth/security/advisories/GHSA-44jh-23m7-hpcf)). Finally, block disposable addresses with the community `better-auth-harmony` plugin, which covers more than 55,000 temporary domains ([better-auth-harmony](https://unpkg.com/better-auth-harmony@1.3.2/README.md)), or with a sign-up hook over the public-domain (CC0) list that PyPI uses ([GitHub](https://github.com/disposable-email-domains/disposable-email-domains)).

Two configuration mistakes would silently void all of this. First, Better Auth exempts server-side `auth.api` calls from rate limiting ([Better Auth](https://www.better-auth.com/docs/concepts/rate-limit)), and the captcha check runs in the same HTTP router hook. A sign-up written as a Next.js server action calling `auth.api.signUpEmail` therefore skips both, so send auth through `/api/auth/*` instead. Second, Railway publishes no client-IP contract. Its staff say the proxy always overwrites `X-Real-IP`, but they decline to give a formal anti-spoofing guarantee ([Railway Station](https://station.railway.com/questions/need-authoritative-railway-client-ip-p-b7a7b4bd)). Set `ipAddressHeaders` explicitly and watch the logs. When Better Auth cannot resolve an IP, it falls back to one shared bucket ([npm](https://registry.npmjs.org/better-auth/-/better-auth-1.7.7.tgz)), which means three sign-ins per ten seconds for every user at once.

### Stripe stays the processor while Postgres owns the counters

Keep `@better-auth/stripe`. It covers checkout, the billing portal, upgrades, downgrades scheduled for period end, annual prices and one trial per user ([Better Auth](https://www.better-auth.com/docs/plugins/stripe)). It processes only four webhook events, though. Handle `invoice.payment_failed` and refunds yourself through `onEvent`, dedupe by event ID, and never depend on event order. Stripe guarantees neither single delivery nor ordering ([Stripe](https://docs.stripe.com/webhooks)). Stripe direct is the cheapest rail at **2.9% + 30¢ plus 0.7% for Billing** ([Stripe](https://stripe.com/pricing); [Stripe](https://stripe.com/billing/pricing)), about 4.2% of a $49 monthly charge. EU and UK consumer sales may grow to the point where registering for VAT becomes a burden. In that case, Polar can act as merchant of record, charging new organisations **5% + 50¢** ([Polar](https://polar.sh/blog/introducing-polar-plans)). It has a Better Auth plugin, so switching is a webhook-mapping exercise as long as quotas stay in your tables. Skip Lemon Squeezy for a new build while it is folded into Stripe Managed Payments ([Lemon Squeezy](https://www.lemonsqueezy.com/pricing)).

### A Postgres queue replaces the orchestration vendor

Run the pipeline on pg-boss in the worker service. It provides retries with exponential backoff, dead-letter queues with redrive, cron scheduling, `SKIP LOCKED` job claiming and LISTEN/NOTIFY wake-ups. It can also **create jobs inside an existing database transaction, with an adapter for Prisma** ([pg-boss](https://github.com/timgit/pg-boss)). That last property is decisive. The API route reserves quota, inserts the report and enqueues its first job in one commit, so the current build's two orphan cases cannot happen: a crash between creating a report and triggering its run, which leaves the report pending forever, and duplicate paid runs from a retried trigger call. graphile-worker is an equivalent choice, with `job_key` deduplication ([graphile-worker](https://worker.graphile.org/docs)). DBOS offers the same Postgres durability in workflow style: a workflow waits on `DBOS.recv`, and the webhook route calls `DBOS.send` ([DBOS](https://docs.dbos.dev/typescript/tutorials/workflow-communication)).

Nothing waits inside a process. The start job persists the visibility prompts first, so a retry can never pair new prompts with old answers; it then calls Bright Data's `/trigger` with an `auth_header` secret, stores the snapshot ID and schedules a timeout job about 16 minutes out. Bright Data's delivery hits a Next.js route that checks the header, dedupes on the `dca-collection-id` snapshot header, acknowledges within the required **30 seconds** and enqueues the analysis job; deliveries arrive gzip-compressed unless the trigger sets `uncompressed_webhook=true` ([Bright Data](https://docs.brightdata.com/products/scrapers/scrapers-library/data-delivery)). The analysis job treats the webhook as a hint and the snapshot as the truth. Snapshots stay downloadable for **30 days** ([Bright Data](https://docs.brightdata.com/products/scrapers/scrapers-library/data-delivery)) and `/progress` reports `ready`, `failed` or `canceled` ([Bright Data](https://docs.brightdata.com/api-reference/scrapers/management-apis/monitor-progress.md)), so the job downloads by ID, validates every row with Zod, and drops and counts error rows, which can appear even in an empty snapshot ([Bright Data](https://docs.brightdata.com/products/scrapers/scrapers-library/faqs)). Below a threshold it fails the report or marks it partial; otherwise it calls Claude, computes metrics in code, and writes `COMPLETED` only through an update guarded on non-terminal statuses. The timeout job polls `/progress` and either resumes the pipeline or cancels the snapshot and releases the reservation, while a scheduled reconciler sweeps anything stale.

Whatever the stack, confirm one billing detail with Bright Data. Its product page says only successful records are billed, while its FAQ says records that fail on bad input are still charged ([Bright Data](https://brightdata.com/products/web-scraper/ai); [Bright Data](https://docs.brightdata.com/products/scrapers/scrapers-library/faqs)).

If owning that engine is unappealing, keep **Trigger.dev Cloud on the $10 Hobby plan**. Its waitpoint tokens expose a callback URL that Bright Data can POST to directly. Waits are checkpointed, so they consume neither compute nor concurrency ([Trigger.dev](https://trigger.dev/docs/wait-for-token); [Trigger.dev](https://trigger.dev/pricing)). It still needs work, for two reasons. `onFailure` and `onCancel` do not fire for crashed runs or runs cancelled while suspended, so a reconciler remains necessary ([Trigger.dev](https://trigger.dev/docs/tasks/overview)). And its compute runs outside Railway, so tasks need a public database endpoint or a callback API.

Do not self-host Trigger.dev on Railway. Self-hosted Trigger.dev has **no checkpoints** and wants at least 7 vCPU and 14 GB across two machines ([Trigger.dev](https://trigger.dev/docs/self-hosting/docker)). The community Railway template puts the supervisor on a separate droplet because Railway offers no Docker socket ([Railway](https://railway.com/deploy/triggerdev)). Inngest is the other managed option. Its functions run inside your Railway app, and `waitForEvent` holds no concurrency slot ([Inngest](https://www.inngest.com/docs/guides/concurrency)). However, its free tier allows five concurrent steps, and Pro starts at $99 a month ([Inngest](https://www.inngest.com/pricing)).

### Server-sent events carry progress while the row stays authoritative

Progress needs no vendor. After each committed state change, the worker issues `NOTIFY` with only the report ID. Payloads must stay under 8,000 bytes and are delivered only after commit ([PostgreSQL](https://www.postgresql.org/docs/current/sql-notify.html)). A Next.js route, authenticated by the Better Auth session, holds a dedicated LISTEN connection rather than one through a pooler. It re-reads the row on each notification and streams Server-Sent Events. Railway closes HTTP requests after five idle minutes and caps them at 15 minutes ([Railway](https://docs.railway.com/networking/public-networking/specs-and-limits)). Send a heartbeat every 15–30 seconds, and let `EventSource` reconnect with `Last-Event-ID`. If you enable Railway's CDN, it never caches or buffers event streams ([Railway](https://docs.railway.com/networking/cdn)). The row is the source of truth and polling is the fallback. A dropped stream therefore shows "reconnecting", not the false failure card that today invites a re-run that spends more quota.

### Call Claude directly and let an eval choose the model

A Claude-only pipeline gains nothing from a gateway hop. Anthropic's structured outputs are generally available through `output_config.format` and strict tools ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). You can reach them from the official SDK, or from the AI SDK's Anthropic provider, which keeps the existing AI SDK 7 code ([AI SDK](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic)). The current Sonnet 5.5 lists at **$2/$10 per million tokens, a third below Sonnet 4.6** ([Anthropic](https://platform.claude.com/docs/en/about-claude/pricing)). It is not a drop-in swap. It rejects the non-default `temperature` the current calls set (0.1–0.2), and it rejects forced tool use. It also thinks adaptively by default, which adds billed output tokens unless you lower the effort level ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/migration-guide.md)). Pick the model with an eval on recorded deliveries. If quality demands a step up, Opus 5.5 costs $4/$20 ([Anthropic](https://platform.claude.com/docs/en/about-claude/pricing)).

Keep Zod validation whatever you choose. Anthropic's structured outputs do not support numeric or length constraints in schemas. Refusals or `max_tokens` stops can also produce output that breaks the schema ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). Keep Vercel AI Gateway only if you want automatic failover to Bedrock or Vertex ([Vercel](https://vercel.com/docs/ai-gateway/models-and-providers/provider-options)). It charges no token markup ([Vercel](https://vercel.com/docs/ai-gateway/pricing)) and already serves RankSEO's workers, which run outside Vercel. OpenRouter takes a 5.5% fee on credit purchases ([OpenRouter](https://openrouter.ai/docs/faq)), which buys nothing a single-provider pipeline needs.

### Agents run the stack through MCP behind guardrails

This stack is as agent-operable as InsForge where it counts. The Railway MCP server already connected to Claude Code exposes **68 tools** (counted on 12 October 2026). They cover logs, metrics, traces, variables, deployments, services, buckets and docs, plus a `railway-agent` delegate. Access uses short-lived OAuth tokens scoped to the projects you choose ([Railway](https://docs.railway.com/ai/mcp-server)). PITR, HA and usage limits remain CLI commands. Better Auth ships a docs MCP server and skills, each installed into Claude Code with one command ([Better Auth](https://better-auth.com/docs/ai-resources/mcp.md)). That matters because the API moves fast. Between 1.4 and 1.7 the CLI was renamed and plugins split into separate packages, and 1.7 itself changed the adapter and rate-limit storage contracts ([Better Auth](https://better-auth.com/docs/guides/1-7-upgrade-guide.md)). Pin the version in `CLAUDE.md`. Stripe's MCP server stops accepting untagged secret and restricted keys on 31 October 2026 ([Stripe](https://docs.stripe.com/mcp)). Everything else is code in the repository: the schema, the quota SQL, the state machine and the auth configuration. There, ECC's database, security and silent-failure reviewers can read it, and its TDD agent can test the quota race with parallel requests ([ECC](https://github.com/affaan-m/ECC)).

Guard the production side. The same Railway toolset includes `delete-volume` and `delete-service`. In April 2026, a coding agent found an account-scoped Railway token and deleted a customer's production database and its volume backups. Railway says the data was recovered, and it has since made all deletes soft for 48 hours ([Railway](https://blog.railway.com/p/your-ai-wants-to-nuke-your-database)). Use OAuth-scoped MCP only, and mark production as restricted. Keep agents on PR environments, and approve every delete and deploy by hand.

## Seven traps to avoid and three risks to own

Seven choices would undo this design. Three are platform traps: making InsForge the system of record in 2026 (if you trial it, keep Compute, the Model Gateway and Sites out of the critical path and account-wide `uak_` keys out of agent context), self-hosting Trigger.dev on Railway, and putting the 15-minute wait inside any BaaS function runtime, whether Supabase's 400 seconds or Nhost's 180. The fourth is treating Railway's safety nets as your own: a hard usage limit takes the whole stack offline, an account-scoped token on disk enabled the April deletion, and volume backups do not survive a deleted project. The fifth is misconfiguring Better Auth by running a version below 1.7.7, writing sign-up as server actions, keeping in-memory rate limits across replicas, or enabling magic link alongside social login without need, a pairing that is a precondition of GHSA-965c ([GitHub](https://github.com/better-auth/better-auth/security/advisories/GHSA-965c-763c-88jm)). The sixth is letting a money path fail open, whether through Autumn's default behaviour, Redis counters that cannot commit with the report row, or two owners of billing state such as InsForge Payments beside the Better Auth plugin. The seventh is carrying MongoDB forward.

The first risk to own is the job engine itself. The recommended path moves durability out of a vendor and into the layer where the current build failed, a build that scored error rows as evidence, wrote statuses without guards and left runs that never terminate. The research puts the work at one to two engineer-weeks, an estimate rather than a measurement. Write the state machine first as pure transition functions with unit tests, replay recorded Bright Data deliveries in integration tests (error rows, duplicates, late webhooks and missing ones), alert on dead-letter queue depth, and keep Trigger.dev Hobby as a ready fallback, since the pipeline steps port either way.

The second risk is Railway. Its 2026 incident reports include two that stopped databases: on 11 February a false-positive abuse rule sent SIGTERM to about **3% of workloads, databases included** ([Railway](https://blog.railway.com/p/incident-report-february-11-2026)), and on 19 May an **eight-hour platform-wide outage** followed Google Cloud's suspension of Railway's account ([Railway](https://blog.railway.com/p/incident-report-may-19-2026-gcp-account-outage)). Contractual SLAs are Enterprise-only, and Pro support answers "usually within 72 hours" ([Railway](https://docs.railway.com/platform/support)). The database features this design leans on are young: PITR shipped in May 2026 and one-click major upgrades in September ([Railway](https://railway.com/changelog)). Still, Railway is an established company. It raised a $100M Series B in January 2026 ([Railway](https://railway.com/changelog/2026-01-23-100m-series-b)) and holds SOC 2 Type II ([Railway](https://docs.railway.com/enterprise/compliance)). Its status page shows 99.98% regional uptime over 90 days ([Railway](https://status.railway.com)). None of its incident reports describes lost data, though one unverified blog alleges corruption during upgrades and volume resizes ([Stack and Sails](https://stackandsails.substack.com/p/railway-reliable-for-nextjs-2026)). Plan for a few hours of downtime a couple of times a year, not data loss. That holds provided offsite dumps exist and you have rehearsed a restore on another provider. Dockerfile builds keep an exit to an estimated day or two of work.

The third risk is Better Auth's pace of change. The project has published **37 security advisories, 27 of them in 2026 and three Critical**, many in enterprise plugins RankSEO would not enable ([GitHub](https://github.com/better-auth/better-auth/security/advisories)). Older minor lines get fixes for only a few weeks. The 1.7.3 patch reverted a 1.7.0 schema change, leaving manual cleanup for anyone who ran 1.7.0 to 1.7.2 ([Better Auth](https://better-auth.com/docs/guides/1-7-upgrade-guide.md)). Vercel's July 2026 acquisition raises a governance question that the MIT licence limits but does not remove ([Vercel](https://vercel.com/blog/vercel-acquires-better-auth)). Budget for frequent upgrades with Renovate and GitHub advisory alerts. Stay on the latest minor, and enable only the plugins the product needs.

One risk sits outside the stack. The reviewed codebase is licensed for personal learning and portfolio use only. A rebuild that reuses its code needs the author's paid commercial licence before it earns revenue ([RankSEO repository](https://github.com/TechWithEmmaYT/AI-SEO-Marketing-SaaS-App)).

## Conclusion

For RankSEO, "agent-native platform or composed stack" turns out to be a false choice. Agent operability is now table stakes: Railway, Supabase, Convex, Better Auth and Stripe all ship MCP servers or docs written for agents, so it no longer separates the options. What separates them is who owns the money-backed state transitions: reserve, collect, analyze, commit and refund. Those transitions are RankSEO's entire risk surface, and they are safest as plain SQL and TypeScript in the repository, where Claude Code can change them and ECC's reviewers and tests can catch regressions, rather than as RLS policies and triggers inside a young vendor's platform. The build order follows from this. Build the platform-independent core first: the schema, quota SQL, entitlement serializer, pipeline state machine and their tests. That core ports unchanged to Railway, Supabase or even InsForge. The host is the reversible decision; the data model is not.

InsForge deserves a second look in 2027 if it does six things: ships durable queues, takes Compute out of preview, adds point-in-time recovery and scoped agent keys, publishes a SOC 2 report, and shows that the BaaS survives InstaCloud. Moving data out of its Postgres is cheap, so adopting it later would carry little regret. Adopting it now would tie RankSEO's revenue to a six-person company's roadmap just as that roadmap turns toward a different product.
